# Contributing

Thank you for looking. Please read the two short sections below before opening
a pull request — this repository works differently from most, and knowing how
saves you the wasted work.

## This repository is published, not developed, here

Development happens in a private repository. What you see here is an **export**:
one commit per release, containing the whole difference since the previous one.
It shares no history with the development repository, which is why `git blame`
and `git bisect` resolve to a release rather than to a change, and why you will
not find the individual commits behind a change.

What that means in practice:

- **Pull requests are welcome and are landed by hand.** A maintainer takes your
  commits into the development repository with `git am`, which preserves you as
  the author there, runs the full gates, and the change reaches this repository
  in the next release's commit. Your name goes in the release note and in a
  `Co-authored-by:` trailer on that commit — but not as a commit of your own in
  this history. That is a real cost of the arrangement and you should know about
  it before you spend an afternoon here.
- **Do not push directly to `main` of this repository.** The next export
  overwrites the tree, and a commit that landed here without being carried back
  would be lost.
- **The CI you see here is feedback, not the gate.** The real gates run on the
  maintainers' self-hosted CI, which drives the same suites plus matrices that
  need real engine accounts. **When GitHub is green and the maintainers' CI is
  red, the maintainers' CI wins.** If that happens on your pull request, ask —
  a maintainer will paste the relevant failure. It may be a sanitised summary
  rather than a full log, because those runs happen on a private machine.

## Identifiers you will see and cannot resolve

Code comments cite `ADR 0031`, `GZH-89`, and case ids such as `ART-021`,
`STO-018`, `ENG-004`, `CONSOLE-012` and `HOST-COMMON-002`. These refer to
decision records, an issue tracker and a test plan the maintainers keep
privately. **The reasoning behind them is not public.** An identifier in a
comment tells you that a line is the way it is deliberately, and roughly what
it is about; it does not tell you why, and no public document reproduces that.
The security-relevant boundaries are the exception — those are summarised, with
their reasons, in [SECURITY.md](SECURITY.md).

If a comment's reasoning matters to a change you are making, ask in the issue
or pull request. Someone will paste it.

## Working on the code

Node ≥ 22, ESM only, pnpm.

```sh
pnpm install --frozen-lockfile
pnpm check          # typecheck → build → test → artifact gate, in that order
```

**Build after editing, before testing.** Several checks read generated output
rather than source, so `pnpm test` on its own can pass against the previous
build. `pnpm check` runs the steps in the right order, which is why it is the
command to use.

Two directories are generated by the build and are not edit targets:
`hosts/*/skills/` (from `skills/`) and the console's UI assets.

The simulated gates need no engine account and no model tokens:

```sh
pnpm release:engines    # the plugin's full path against a scripted agent
pnpm release:workflow
pnpm release:console
```

## What a good pull request looks like here

- One self-contained change with its tests. Roughly 300 lines is comfortable;
  1000 is too large and will be sent back to be split.
- Tests that would go red without the fix. Please check that by removing the
  fix and watching the test fail — several tests in this repository's history
  passed against unfixed code.
- Comments that say **why**, not what. If a comment states that something is
  checked, the check should exist.
- English, in code and in commit messages.

The tool surface is **frozen at 20 tools** and the artifact gate asserts it.
Adding one is not a pull request; it is a decision, and it needs a maintainer to
make it first. Open an issue instead — a new parameter on an existing tool is
usually the answer.
